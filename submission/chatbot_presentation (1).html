How the Chatbot Works
Multi-Agent
Customer Service
for Golf Gear Pro
This chatbot handles product questions, order lookups, and refund requests — all in the same conversation. Instead of one giant agent trying to do everything, it uses a router that classifies each message and sends it to the right specialist.
Technology Stack
LLM Ollama llama3.1:8b · runs locally
Orchestration LangGraph StateGraph + MemorySaver
Vector Store Chroma Product feature retrieval (RAG)
Data Files CSV + Text golf_products.csv · golf_orders.csv · store_policies.txt
The Four Specialist Agents
🏌️
Product Q&A Agent PRODUCT
Answers questions about golf gear — specs, pricing, compatibility. Uses RAG over a Chroma vector store to retrieve product descriptions, plus a direct price lookup tool over the CSV.
getproductprice GetProductFeatures
📦
Orders Agent ORDER
Looks up and updates customer orders by order ID. Can check status, retrieve details, and change an order's status (e.g. mark as Delivered).
getorderdetails updateorderstatus
↩️
Refund Agent REFUND
Handles return and refund questions by looking up the relevant section of store_policies.txt based on topic (damaged items, general returns, shipping, cancellations).
getrefundpolicy
💬
Small Talk Handler SMALLTALK
Handles greetings, farewells, and off-topic chat directly inside the router graph using its own system prompt — no specialist agent needed.
Router Dispatch — How a Message Gets Routed
Every incoming message is first sent to the Router LLM, which reads the message and returns exactly one word. That word determines which agent handles the response.
PRODUCT → Product Q&A Agent (Chroma RAG + price lookup)
ORDER → Orders Agent (lookup / update by order ID)
REFUND → Refund Agent (policy lookup by topic)
SMALLTALK → Small Talk node — handled inline by the router
END → Default fallback for out-of-scope messages
LangGraph Router Graph (generated at runtime)
The Router node sits at the center. Conditional edges fan out to each specialist. All paths converge back at __end__.

Orders Agent Graph (notebook 04)

Memory & State Handling
How the Chatbot
Remembers Context
LangGraph's MemorySaver acts as an in-process checkpoint store. Every time the graph is invoked with the same thread_id, it automatically reloads the prior conversation state — including the full message history — before running. No external database is needed.
Code Pattern — From the Notebooks
# A new thread_id is created for each user session config = { "configurable": { "thread_id": str(uuid.uuid4()) }, "recursion_limit": 6 } # MemorySaver is attached at compile time self.graph = graph.compile( checkpointer=MemorySaver() ) # Each invoke call persists + restores state # automatically for that thread_id result = router_agent.router_graph.invoke( {"messages": [HumanMessage(user_input)]}, config=config )
What MemorySaver actually stores: After each turn, LangGraph checkpoints the entire RouterAgentState — including all prior messages — and associates it with the thread_id. On the next invocation with the same thread, that state is rehydrated before the graph runs. This is why Turn 4 in the demo ("How much does it cost?") worked — the prior messages about the FairwayPro Iron Set were still in the thread's state.
Each specialist gets its own thread: When the Router dispatches to a specialist agent, it passes the same thread_id via agent_config. This means the Orders agent, Product agent, and Refund agent each maintain their own memory within the same session.
SupervisorState — What Gets Persisted Per Checkpoint
messages list Full conversation history. Uses operator.add so new messages append rather than overwrite — the entire thread is always preserved.
plan str A one-line intent description written by the Planner node before execution. Helps the Executor understand what it's trying to accomplish.
route str PRODUCT / ORDER / REFUND / SMALLTALK — set by the Executor so downstream nodes know which specialist was used.
reflection_decision str CONTINUE or SUMMARIZE — written by the Reflection node. Drives the conditional edge that decides whether to retry or finalize the answer.
attempt_count int Incremented by the Executor each pass. Prevents infinite loops — the Supervisor gives up and summarizes once max_attempts (2) is reached.
AgenticSupervisor Pipeline
1
Planner
Reads the last HumanMessage from state and writes a one-line plan describing the intent. This frames the task for the Executor.
2
Executor
Invokes the RouterAgent with the full message list. Increments attempt_count. Appends the agent's AIMessage response to state.
3
Reflection
An LLM judges whether the answer actually satisfied the user's request. Returns exactly one word: CONTINUE or SUMMARIZE.
4a
→ Back to Planner (if CONTINUE)
If the answer was unsatisfactory and attempt_count < max_attempts, loop back and try again with a revised plan.
4b
Summarizer → END
Rewrites the draft answer into a clean, user-facing response and writes the final AIMessage to state. Observed: ATTEMPTS=1, REFLECTION=SUMMARIZE — satisfied on the first try.
